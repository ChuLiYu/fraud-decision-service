## 問題

收到一筆非實體卡交易，產生詐欺風險分數，依版本化政策轉成放行／送審／拒絕，並保存完整紀錄，讓任何決策都能說明、重播，並在標籤到達後評估。所有決策皆為模擬。

## 定位

作品集專案，主投「專長為把 ML 模型帶進正式環境」的後端職位，次要對應 ML 平台／MLOps 職位。模型訓練維持正確但精簡；工程投入集中在服務化、決策可靠性、上線流程與可觀測性。

## 讀者

- 檢視 repo 的招募主管與面試官。
- 實作本專案的擁有者與協作 Agent。

## 範圍外

- 真實付款、卡組織、銀行或客戶資料。
- AML、KYC 或法規申報。
- 自動重訓或自動升級模型。
- 自建 feature store、service mesh 或多區域部署。
- 為了展示而加入的 LLM 功能。
- 雲端部署與基礎設施即程式碼（AWS、Terraform）；擁有者已以其他經歷證明這些能力。
- 資料無法支持的帳戶或身分關聯（卡片欄位不視為已驗證的客戶身分）。

## 架構摘要

決策為同步：呼叫端等待放行／送審／拒絕。Kafka 承載處理時不能增加請求延遲的事件（shadow 評分、標籤配對、重播）。服務分工記錄於 [ADR-002](../decisions/ADR-002-java-decision-python-inference.md)。

## 階段與驗收

每項條件都在 repo 中有證據（測試、報告或 CI 執行紀錄），該階段才算完成。目標不是結果。

### 第 1 階段：可信的模型（S-1）

- 一個命令即可從下載的資料集重現資料準備、訓練與評估。
- 依 `TransactionDT` 切分 train／validation／test；前處理只用訓練資料擬合。
- 報告包含 ROC-AUC、PR-AUC、固定送審比例下的 precision／recall、校準檢查、各時間區段結果，並與 baseline 比較。
- 資料限制記錄於 [dataset card](../data/dataset-card.md)。

### 第 2 階段：同步決策服務（S-2 到 S-5、S-10）

- 實作前已有評分與決策 API 的 OpenAPI 契約。
- 決策保存請求雜湊、模型版本、政策版本、分數、結果與延遲。
- 同一個冪等鍵的併發重複請求只產生一筆決策。
- 推論服務停止、變慢或回錯時，決策為 `review`，並記錄降級路徑。
- 未驗證的服務呼叫會被拒絕。
- 在固定樣本上，離線與線上分數在註明的容差內一致。
- CI 執行單元測試與 Testcontainers 整合測試。

### 第 3 階段：事件與 shadow 評分（S-6、S-7、S-13）

- 在資料庫提交與事件發布之間終止決策服務，不遺失事件，也不產生幽靈事件。
- Consumer 能承受重複傳送與重啟，不重複處理。
- Shadow 評分對請求延遲的影響在註明容差內；比對結果有保存。
- 一次向後相容的事件 schema 變更，在 CI 通過 registry 相容性檢查。

### 第 4 階段：上線、特徵與可觀測性（S-8、S-9、S-11、S-12、S-16）

- Canary 分流把設定比例的流量送到候選模型；回退一步恢復前一版。
- Redis 無法使用時，服務依文件中的降級模式運作。
- 一條 trace 呈現單筆決策經過的每一段；儀表板涵蓋延遲、錯誤、consumer lag、特徵缺值率與分數分布。
- 壓測報告註明硬體、資料量、併發、吞吐量、p99 延遲與錯誤率。

### 第 5 階段：Kubernetes 部署（S-14）

- 以 Helm 部署到本機 Kubernetes；新模型版本 readiness 通過後才接流量。

## 限制
